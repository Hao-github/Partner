# 待优化项评审

为当前目标选择值得推进的优化方向，给出有证据的取舍和可执行方案。所有项目路径以本仓库根目录为基准；本技能由 Codex 使用。

## 按需发现

- 先看 git status 与最近提交，再读 [待优化索引](../../../docs/plans/optimizations/README.md)。保留并行改动，评估以当前源码为准。
- 按用户目标、实际触发条件和维护负担初筛，通常深入不超过 3 项；只打开入选条目的详情、相关源码和必要测试。其他项只做索引初筛时，要说明核验范围。
- 只有阶段优先级不清楚时读 [roadmap](../../../docs/plans/roadmap.md) 的相关段落；只有怀疑已完成时查归档的对应编号/提交。不要批量加载 docs、全部详情和历史。

## 比较与方案

- 核对问题是否仍存在、实施条件是否已满足、是否已有等价实现。名称或模式相同不等于范围相同；局部实现不能代表整个条目完成。
- 比较当前收益与条件满足后的收益、实现成本、依赖和不确定性。明确收益属于维护性、可靠性、体验还是性能；未经测量不填提升百分比或精确工期。
- 对入选项说明：可行性及源码依据；改动规模与模块/接口/配置/数据库/兼容性的影响；预期收益；tradeoff 与更简单的替代；最小实施步骤；验证和回退方式。没有涉及的影响面可合并说明。
- 优先解决当前真实问题，选择能够兑现收益的最小改动；必要时建议先做 roadmap 中的可靠性能力。允许结论为“目前没有值得立即实施的 OPT”，不要为了凑数放宽条件。

## 交付与记录

先给推荐顺序和“现在做 / 条件满足后做 / 继续暂缓”的结论，再用比较表及入选项方案说明依据，链接相关条目和源码。区分已核验事实、预期收益与待验证假设。

评审本身不代表用户要求实施；若同时要求落实，则继续在已授权范围内工作。不要把仅评审的条目标为进行中或已完成。

有新结论、来源或条件变化时，按 [维护流程](../../../docs/plans/optimizations/process.md) 更新对应条目和索引；新想法先去重再编号。需要保存比较结果时更新 `docs/plans/optimizations/review.md`，只保留摘要与详情链接，不复制整份方案。

Codex 开发技能可直接评审仓库；GPTPartner 的 QQ/CLI Agent 是否支持运行时 Skill，应另外核对代码与 M3 验收，不因本技能存在就宣称已支持。
