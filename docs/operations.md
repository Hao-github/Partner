# 运行与可靠性

状态：现有本地行为与待实现的云端运行方案。尚无服务器、systemd 配置或部署产物；本文不表示已上线。优先级和验收进度见 [演进与验收](roadmap.md)。

## 当前运行边界

当前主要入口为 `python main.py --channel qq` 或 `python main.py --channel cli`，一个 Agent 管理一个渠道。QQ 主动建立出站 HTTPS / WebSocket 连接，没有业务 HTTP 监听端口。检查和识别模式说明见 [QQ 文档](../ai_butler/channels/qq/README.md)。

已有请求超时、有限重试、QQ 心跳与重连、SQLite 回复缓存、白名单和限速。尚无独立补发、全轮截止时间、SIGTERM 关闭处理、常驻健康探测或备份任务。--check 只验证凭据和网关，不验证消息权限或模型推理；进程存活也不等于业务可用。

## 小型 Linux 服务器方案

沿用已讨论的单台 Linux 云服务器、Conda gptpartner、SQLite 和 systemd 管理方案。1–2 核、2 GB 内存、20 GB 以上磁盘仅是初始估算，需根据实际依赖、数据增长和模型请求负载验证。当前通过模型 API 推理，不在服务器部署本地大模型。

| 项目 | 设计约定 |
| --- | --- |
| 发行版和地区 | 选择受支持的 Linux LTS；购买前实测 QQ 与实际模型服务的访问条件和延迟 |
| 进程 | 单实例运行同一机器人；部署与回退时先停止旧实例 |
| 账户 | 使用专用服务账户，限制配置、数据库和备份目录访问 |
| 程序目录 | 固定工作目录，启动前激活 gptpartner，使用 exec 把 Python 作为服务主进程 |
| 配置 | .env 仍由 config.py 加载；部署系统不再创建第二套 .env 解析逻辑 |
| 状态 | BUTLER_DB_PATH 指向发布目录之外的持久绝对路径，避免更新代码覆盖数据 |
| 网络 | 当前业务仅需出站连接；管理入口按实际运维方式配置 |
| 监督和日志 | systemd 管理重启与启动频率限制，标准输出交由 journald 收集 |

实际服务文件需在停止信号、退出码和超时策略实现后提供，不能只靠 Restart 配置掩盖持续失败。systemd 的重启策略需结合退出原因、停止超时和启动频率限制设置。[systemd 服务说明](https://freedesktop.org/software/systemd/man/latest/systemd.service.html)

依赖版本在发布时记录，复现失败时可还原对应环境；不以持续安装最新依赖作为发布方案。

## 生命周期与恢复

目标流程为停止接收入站消息、设置停止事件、关闭网关、取消排队任务、在明确期限内结束当前工作并释放资源。SIGINT 与 SIGTERM 应进入同一幂等关闭路径；异常退出由服务监督恢复。信号处理器保持简单，不在其中直接阻塞等待线程退出。

当前 QQ 同步 HTTP 调用无法立即取消，close 会等待运行中的工作线程。因此需同时确定请求超时、整轮截止时间、停止期限和服务管理器的停止超时；超过期限的工作不能无限阻止发布或关机。预期配置错误、可恢复连接失败和永久权限错误要使用可区分的退出/重启策略。

恢复时保留 SQLite，不清空历史。模型轮次只有成功后才保存；已保存但未发送的回复与尚在内存队列中的请求不是同一种状态，不能把所有任务都视为已持久化。

## 交付恢复设计

当前成功路径为生成、事务保存、平台发送、单独标记 sent。平台重推可以复用缓存；发送重试耗尽且平台没有重推时，不会自动补发。队列满时当前只写固定警告日志，消息不入库。

主动补发需要在 storage 增加足够的投递数据，而非仅扫描 deliveries.sent：

| 数据/规则 | 用途 |
| --- | --- |
| 渠道、账户、目标、原消息标识 | 重启后能够重建合法发送请求 |
| 创建时间、可发送期限 | 避免原消息关联或平台回复窗口失效后无限重试 |
| 尝试次数、下次尝试、状态 | 限制重试并区分待发送、成功、永久失败或过期 |
| 幂等键及平台重复响应处理 | 缩小发送成功但标记失败时的重复窗口 |

新回复、对话变化及待投递记录应同一事务提交。队列调度和平台发送使用各自短生命周期，发送不占数据库写事务。前台和补发必须协调同一投递的所有权，防止并发重复发送。平台限制无法满足时记录过期或失败，不擅自改成主动消息。

队列满的提示与重试策略放在渠道侧，不能让心跳线程等待模型或长期阻塞在发送请求上。首版仍保持有界队列和串行工作，不因为补发就引入分布式队列。

## 备份、迁移与发布

当前可采用停进程后确认连接释放、再备份 SQLite 的方式。运行中备份应使用 SQLite Backup API 等一致性机制，不把直接复制活跃数据库文件当作通用方案。[SQLite 备份说明](https://www.sqlite.org/backup.html)

建议初期每日备份、变更表结构前额外备份，并保留最近 7 个日备份；这是待配置策略，需结合私人数据保留需求调整。备份放在独立受控位置，包含校验信息和生成时间，不进入 Git。

恢复验收在隔离位置进行：检查数据库完整性，确认表结构可由目标版本读取，并用测试数据验证历史、会话模型及投递状态。备份成功日志不能代替实际恢复验证。文档和日志不输出真实聊天内容。

发布顺序：

1. 激活 gptpartner，运行单元测试、Ruff 和 Pyright；记录目标提交和依赖版本。
2. 停止旧实例并备份状态，确认没有本地与云端双实例。
3. 更新代码和依赖；涉及旧表变化时先按版本迁移，再启动服务。
4. 检查网关在线、一次真实模型/工具回复及重启后的会话恢复。
5. 失败时停止新实例；先判断 schema 兼容性，再选择代码回退或数据库恢复。恢复旧库会丢弃备份后的新数据，不能自动覆盖当前库。

本机迁云同样遵循停止、备份、独立传输、检查、启动、验证的顺序。私人配置和数据库通过受控方式迁移，Git 只迁移代码与通用文档。

## 可观测性和验收

当前日志已记录安全的状态、耗时和重试信息，不记录凭据、用户标识或聊天正文。后续优先增加最近业务成功时间、队列数量、失败计数、投递状态和用量等元数据；个人部署可先使用本地状态和日志，不急于搭监控平台。

常驻验收至少包含：SIGTERM 退出和重启、网络断开恢复、模型超时/限流、发送失败恢复、队列满、磁盘/数据库错误、备份恢复，以及一段真实长时间运行。明确记录测试时间与结果，再将相应状态改为已完成。
