## 已完成事项归档 · 2026-11-06

OPT-009 至 OPT-012 来源于本轮设计模式讨论对现有实现的确认，日期为回溯核验/归档日期，不推测最初完成时间。原开发记录保留在下文；后续每个完成项也应保留提出来源、评估、实际结果和验证证据。

### M0

**文本聊天 MVP（已完成，现有基线）。** CLI / QQ 官方 C2C 文本、SQLite 历史、模型切换、工具循环与缓存回复已实现。基线记录见 27a6ae4，后续协议与工厂调整见 dbb2c99、99440c7。既往 QQ 真实联调沿用现有交接记录，本轮未重新联网验证；不包含长期记忆、MCP、后台任务和云端部署。

### OPT-009

**Agent 统一入口与内部简单工厂（已完成，回溯核验）。**

- 问题/方案：将运行、关闭、诊断和组件选择集中到 Agent 与内部工厂，新增实现只扩展对应实现和类型选择分支。
- 评估：可行性高；优化度中，减少应用层组合和名单耦合；成本小，需保持具体协议留在各自层。
- 实际结果：Agent 公开 run / close / inspect；Provider 默认配置由子类声明、工厂应用；Agent、CLI 和存储不维护供应商名单。
- 证据：core/agent.py、providers/__init__.py、channels/__init__.py；test_app.py 的第三种 Provider/Channel 扩展、诊断与关闭流程测试。历史提交 dbb2c99、99440c7。

### OPT-010

**Provider 策略与协议适配（已完成，回溯核验）。**

- 问题/方案：供应商请求、认证和响应格式各自适配，对内通过 complete 返回统一消息；基类仅共享 HTTP/JSON 与有限重试。
- 评估：可行性高；优化度中，使模型循环复用、供应商差异局部化；成本中，风险是统一消息契约不能覆盖未来新能力。
- 实际结果：OpenAI / DeepSeek 直接继承 Provider，独立维护参数、解析及安全错误提示。新媒体等超出当前契约的能力仍需显式设计。
- 证据：providers/_base.py、_openai.py、_deepseek.py，test_providers.py 和 test_app.py。历史提交 dbb2c99、99440c7。

### OPT-011

**Channel 公共流程模板（已完成，回溯核验）。**

- 问题/方案：历史、会话模型、缓存去重、保存、发送状态与关闭规则统一维护，平台子类实现接收、发送和资源清理钩子。
- 评估：可行性高；优化度中，减少渠道复制公共业务规则；成本中，需避免把平台差异堆进基类。
- 实际结果：Channel._process 负责公共流程；CLI / QQ 通过统一 IncomingMessage 和 Reply 交互，不直接操作存储连接。
- 证据：channels/_base.py、cli/_channel.py、qq/_channel.py，test_channels.py、test_qq.py 和 test_app.py。历史提交 dbb2c99。

### OPT-012

**SessionStore 原子保存（已完成，回溯核验）。**

- 问题/方案：完整轮次、会话模型和回复缓存同一事务保存，存储层管理连接与 SQL。
- 评估：可行性高；优化度高，避免相关写入只完成一部分；成本小，发送与本地标记之间仍有重复窗口。

- 证据：storage/sessions.py、test_storage.py、test_channels.py，以及 test_app.py 的会话选择与旧命令重推验证。历史实现已存在，本轮未调整事务或表结构。
