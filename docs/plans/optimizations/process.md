# 优化项维护流程

读取条件：新增想法、重新评估或变更状态。实施既有项时先读 [索引](README.md) 与对应详情。

docs 作为仓库内轻量事项追踪：先记录需求与评估，再按实际进展流转，核验后归档。相关项通过稳定编号标明依赖、关联或替代关系；同一改动只维护一份实施任务与验收证据，索引、设计及交接链接该记录。

## 记录与评估

- 每项使用稳定编号，保留来源、提出/更新日期、场景、方案、可行性、优化度、成本/风险、实施条件、验收标准与状态。复用已有条目补充新结论，编号不重排、不复用。
- 可行性：高表示现有扩展点可支持；中表示需要补齐契约或验证外部条件；低表示关键条件尚不具备。评估以当前源码为准。
- 优化度指预期收益：高表示解决核心可靠性/维护问题；中表示在明确扩展场景下减少重复或耦合；低表示当前收益有限或新增复杂度较高。区分当前收益与触发条件满足后的收益，不代表实测提升。
- 成本按改动范围分小/中/大，同时注明风险。优先级综合收益、成本和依赖决定，不按模式名称或条目顺序决定。
- 状态使用待评估、候选、进行中、暂缓。候选表示方案可供选择，尚未排期；进行中只用于实际开始实施的工作。
- 完成项将完整记录移到 [CHANGELOG](../../archive/CHANGELOG.md)，[归档索引](../../archive/README.md)保留已完成状态及链接。部分完成仍留在计划，注明剩余验收；新增独立范围另建编号。重启原事项沿用编号并保留既有归档。
- 完成需有实际结果与相应验证；文档完成不代表功能完成。历史项注明核验日期，不推测最初完成日期。

## 文件与状态流转

- 未完成详情放在本目录的 `opt-xxx.md`，索引只保留摘要、状态、评估和链接；来源与日期在每份详情内保留。先搜索编号或关键词去重，不批量展开所有详情。
- 完成并验证后，将完整条目迁至 [CHANGELOG](../../archive/CHANGELOG.md)，删除待优化详情及其待办行，并更新 [归档索引](../../archive/README.md)；原编号、结论与证据永久保留。
- 部分完成仍保留详情并列出剩余条件；重新开启时恢复同编号详情、链接原归档，归档索引注明重开，不覆盖旧结果。
- 新条目至少包含：编号/标题、状态、来源及提出/更新日期、问题、方案与模块、可行性与理由、优化度与理由、成本/风险、依赖/实施条件、验收标准。
- 新想法默认只维护单项灵感文件与本目录索引；复评也优先只改该项。完成时删除详情，更新优化/归档索引并保留完整归档，不因讨论或状态变化同步改写其他 docs。
- 只有实际接口、配置、使用方式变化或删除详情导致引用失效时，才修改相应必要说明；不在多份文档中重复维护方案、状态和测试数量。归档读取具体编号或日期段落，文件增长后按实际年份拆分。

## 继续保持的设计

继续使用 Agent 门面、Provider 策略/适配器、内部简单工厂、Channel 模板方法和 SessionStore 事务封装。建造者、强制单例和动态插件加载没有当前问题支撑，暂不作为实施待办；出现复杂构造、生命周期约束或第三方动态安装需求时，先记录场景与评估。

新增上下文、记忆、MCP、Skill、睡梦整理和常驻运行等能力继续由 [roadmap](../roadmap.md)、[能力设计](../../design/capabilities.md)、[运行与可靠性](../../guides/operations.md) 定义范围。上述优化只随真实用例选择，不取代已有可靠性目标。
