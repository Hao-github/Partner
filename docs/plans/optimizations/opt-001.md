# OPT-001

状态：候选；提出/更新：2026-11-06（Asia/Shanghai）。来源：设计模式与项目架构优化讨论中的建议，尚未实施。

涉及模块与验证落点：[工具注册](../../../ai_butler/tools/registry.py)、[时间工具](../../../ai_butler/tools/clock.py)、[工具与循环测试](../../../tests/test_core.py)。

**工具命令与统一注册表。** 当前 `tools/registry.py` 分开维护 TOOL_SCHEMAS 和名称分发，只有一个时间工具，暂未出现维护负担。

- 方案：在 tools 层以小型 Tool dataclass 关联 schema 与执行函数，用字典按名称查找；描述和执行入口从同一注册表产生。JSON 解析放在接入边界，具体参数校验留给工具。未来 MCP 在工具层适配，Agent 不维护服务器名单。
- 评估：可行性高，可复用现有执行入口；当前优化度低，工具增多后为中，可减少漏注册和描述/执行不一致。成本小；风险是新增无职责的工具继承层或改变现有错误语义。
- 实施条件：新增第二个实际工具或首次接入 MCP 时，与该能力一起实施；资源关闭和调用上下文随真实需求补齐。
- 验收：多工具描述与执行一致；重名有明确处理；未知工具、无效 JSON 和参数错误有可预测结果；工具结果仍进入完整轮次；现有时间工具行为保持兼容。

## 2026-11-06 复评

- 结论：扩展时首选候选，当前继续等待第二个运行时工具。Codex 开发技能不会进入 Agent 的工具列表，不能作为本项触发条件。
- 改动与收益：tools 层的小改动，主要减少描述与执行入口不一致；Provider、渠道、数据库和公开 Agent API 无需变化。只有一个工具时，当前分支更短。
- 实施方案：将 schema 与执行函数组成 Tool 数据类并建立显式字典；由字典派生描述和分发，保持现有工具结果 JSON 契约；用测试专用第二个工具验证多工具、重名与错误路径，再随实际新工具上线。
- tradeoff / 验证与回退：增加少量注册结构，换取扩展一致性；不引入插件扫描或工具类继承体系。覆盖 tests/test_core.py 及现有端到端工具流程，执行三项项目检查；回退只涉及工具模块及对应测试，无数据迁移。
