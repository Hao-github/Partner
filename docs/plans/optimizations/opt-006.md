**进程内事件与订阅。** 当前日志与回复直接调用，没有多个独立订阅者。

- 方案：只有同一业务事件需要审计、统计、通知等多个独立消费者时，才评估观察者；先明确同步/异步、异常传播和资源释放规则。
- 评估：可行性中，事件契约和失败语义尚未确定；当前优化度低，真实多消费者场景下为中。成本中；风险是隐式执行顺序、重复副作用或不可追踪的后台失败。
- 暂缓原因/触发：当前直接调用更清楚；不为单个日志动作创建事件总线。
- 验收：订阅者失败行为明确；主流程结果一致；重复事件的处理有定义；事件只携带必要数据，不包含凭据或私人正文。

## 2026-11-06 范围澄清与复评

来源：用户询问 OPT-006 是否本质上需要 Kafka，以及对当前项目是否过重。结论：保持暂缓，限定为进程内观察者/回调机制，不引入 Kafka 或其他外部消息代理；原编号与评估记录保留。

发布/订阅是一种协作方式，可以用普通函数回调实现。Kafka 是提供事件发布订阅、持久保存和分布式处理能力的独立平台，需要服务端与客户端，并管理 topic、分区和消费进度。它是特定场景下的实现选择，不是观察者模式的必需组件。[Apache Kafka 官方介绍](https://kafka.apache.org/intro/)

| 场景 | 最小选择 | 当前判断 |
| --- | --- | --- |
| 一个流程调用一个明确后续动作 | 直接调用函数 | 继续使用，调用顺序和失败传播最直观 |
| 同一事实需要通知多个独立模块 | 进程内回调列表或简单订阅表 | 达到原触发条件后再评估，不预建事件总线 |
| 少量任务或补发需要重启恢复 | 评估现有 SQLite 中的任务/投递记录和游标 | 持久化需求单独设计，内存回调不提供恢复保证 |
| 多个独立服务需要持久事件流和独立回放 | 重新评估消息中间件 | 当前没有需求，不预设 Kafka 为最终方案 |

- 可行性仍为中：回调本身实现简单，但具体事件契约、执行顺序、异常传播和线程归属尚需真实用例确定。
- 优化度仍为当前低、触发后中：目前直接调用已经清楚。单进程个人负载下，Kafka 带来的独立服务部署、存储、消费恢复和监控成本缺少对应收益；这是基于项目现状的判断，没有性能或资源提升比例。
- 成本仍按完整事件契约评估为中；最小回调实现可以很小，不应因此扩展为通用消息框架。只有处理器确实需要异步执行时，才额外定义有界排队、关闭和失败行为。
- 新增验收约束：进程内通知不声称持久化或可靠投递；需要事务成功才能发生的通知在提交后触发，关键业务写入仍使用明确的用例与事务。需要可靠审计或补偿时，另外定义持久化和幂等，不依赖一次内存回调。
