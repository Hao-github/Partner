# 项目优化计划

建立/更新：2026-11-06（Asia/Shanghai）。记录对话中形成的优化方向及评估，不构成实施承诺。阶段目标见 [演进与验收](roadmap.md)，现有实现见 [架构设计](architecture.md)。

## 记录与评估约定

- 每项使用稳定编号，保留来源、提出/更新日期、场景、方案、可行性、优化度、成本/风险、实施条件、验收标准与状态。复用已有条目补充新结论，编号不重排、不复用。
- 可行性：高表示现有扩展点可支持；中表示需要补齐契约或验证外部条件；低表示关键条件尚不具备。评估以当前源码为准。
- 优化度指预期收益：高表示解决核心可靠性/维护问题；中表示在明确扩展场景下减少重复或耦合；低表示当前收益有限或新增复杂度较高。区分当前收益与触发条件满足后的收益，不代表实测提升。
- 成本按改动范围分小/中/大，同时注明风险。优先级综合收益、成本和依赖决定，不按模式名称或条目顺序决定。
- 状态使用待评估、候选、进行中、暂缓。候选表示方案可供选择，尚未排期；进行中只用于实际开始实施的工作。
- 完成项将完整记录移到 [CHANGELOG](../CHANGELOG.md)，本文件保留“已完成”索引及链接。部分完成仍留在计划，注明剩余验收；新增独立范围另建编号。重启原事项沿用编号并保留既有归档。
- 完成需有实际结果与相应验证；文档完成不代表功能完成。历史项注明核验日期，不推测最初完成日期。

### OPT-001

**工具命令与统一注册表。** 当前 `tools/registry.py` 分开维护 TOOL_SCHEMAS 和名称分发，只有一个时间工具，暂未出现维护负担。

- 方案：在 tools 层以小型 Tool dataclass 关联 schema 与执行函数，用字典按名称查找；描述和执行入口从同一注册表产生。JSON 解析放在接入边界，具体参数校验留给工具。未来 MCP 在工具层适配，Agent 不维护服务器名单。
- 评估：可行性高，可复用现有执行入口；当前优化度低，工具增多后为中，可减少漏注册和描述/执行不一致。成本小；风险是新增无职责的工具继承层或改变现有错误语义。
- 实施条件：新增第二个实际工具或首次接入 MCP 时，与该能力一起实施；资源关闭和调用上下文随真实需求补齐。
- 验收：多工具描述与执行一致；重名有明确处理；未知工具、无效 JSON 和参数错误有可预测结果；工具结果仍进入完整轮次；现有时间工具行为保持兼容。

### OPT-002

**通用聊天命令分发。** 目前 core 处理 `/model`，CLI 处理终端命令，分工合理；只有一个跨渠道业务命令。

- 方案：通用命令增加时，在 core 用“命令名 → 处理函数”分发，处理器返回 Reply；CLI 的退出、帮助呈现和终端会话交互继续留在渠道。使用函数即可，不预建命令总线或类层次。
- 评估：可行性高，已有统一 IncomingMessage / Reply；当前优化度低，多条通用命令时为中。成本小；风险是将终端交互混入业务，或在各渠道重复维护通用命令名单。
- 实施条件：新增第二个跨渠道业务命令，例如已明确语义的记忆命令；与 roadmap M2 等实际用例结合。
- 验收：CLI/QQ 的通用命令行为一致；普通聊天不误判；模型切换仍不调用模型、不写模型历史；失败及旧消息重推不覆盖新选择；CLI 本地命令继续可用。

### OPT-003

**内部依赖注入与模型循环边界。** Config 和消息处理回调已通过参数传入；现有模型循环测试仅需替换一个工厂，当前 Agent 规模可控。

- 方案：必要时让内部模型循环显式接收 Provider 与工具执行器，Agent 保持统一公开入口并在内部组装；只在出现独立职责时拆出模块。
- 评估：可行性高；当前优化度低，复杂替换或复用场景下为中。成本中；风险是增加转发层、公开多套运行入口，或把工厂/模型缓存职责分散。
- 暂缓原因/触发：单个工厂 patch 已满足测试；待共享工具上下文、资源生命周期或独立复用使边界确有价值后重评。
- 验收：内部循环可用显式测试依赖执行；生产仍由 Agent 启动；模型缓存、选择、失败处理和完整轮次不变；模型 mock 仅在 tests。

### OPT-004

**模型调用的观测能力组合。** Provider 基类已记录 HTTP 耗时、重试与状态，当前无重复指标采集需求。

- 方案：未来需要多个可组合观测能力时，再评估 Provider 包装器/装饰器；仍将供应商协议留在各实现，有限重试留在现有传输边界。
- 评估：可行性高，complete 接口稳定；当前优化度低，跨供应商复用指标时为中。成本小；风险是重复重试、重复计数，或把正文和凭据写入指标。
- 暂缓原因/触发：现有安全日志已够用；优先明确运行指标，再判断普通共享函数是否已经足够。
- 验收：仅记录必要元数据；失败、重试与工具轮次计数语义明确；装饰前后返回值和异常行为一致，不改变请求次数。

### OPT-005

**按需引入执行处理链。** 当前白名单、限流和工具参数校验有明确所属边界，无需统一流水线。

- 方案：当多项执行规则确实共享时，再定义有明确顺序、短路与失败语义的处理链；工具权限校验放在实际执行边界，渠道限速留在渠道。
- 评估：可行性中，需先确定执行上下文和业务规则；当前优化度低，规则复用明确后为中。成本中；风险是过度校验、跨层耦合和隐藏控制流。
- 暂缓原因/触发：首个有副作用工具或复杂规则出现时先评估，可与 roadmap M3 的工具执行上下文一起设计。
- 验收：规则顺序与拒绝结果明确；拒绝不执行副作用；不在标准响应内部重复逐字段校验；必要的拥有者与请求上下文正确传递。

### OPT-006

**内部事件与订阅。** 当前日志与回复直接调用，没有多个独立订阅者。

- 方案：只有同一业务事件需要审计、统计、通知等多个独立消费者时，才评估观察者；先明确同步/异步、异常传播和资源释放规则。
- 评估：可行性中，事件契约和失败语义尚未确定；当前优化度低，真实多消费者场景下为中。成本中；风险是隐式执行顺序、重复副作用或不可追踪的后台失败。
- 暂缓原因/触发：当前直接调用更清楚；不为单个日志动作创建事件总线。
- 验收：订阅者失败行为明确；主流程结果一致；重复事件的处理有定义；事件只携带必要数据，不包含凭据或私人正文。

### OPT-007

**QQ 网关显式状态对象。** 现有 QQGateway 已用状态变量、停止事件和 match 表达登录、心跳、恢复与重连，不是缺少状态管理。

- 方案：状态转换难以维护时，再评估枚举、转换表或 State 对象；先采用能够消除真实重复的最小表示。
- 评估：可行性高；当前优化度低，复杂状态重复出现时为中。成本中；风险是增加状态类数量或漏掉心跳/恢复转换。
- 暂缓原因/触发：现有实现与测试已覆盖主要流程；不能仅因协议有状态就引入 State 类层次。
- 验收：Hello/登录期限、READY/RESUMED、心跳确认、无效会话、断线重连和关闭行为均有验证；已登录连接不再受初始登录期限限制。

### OPT-008

**仓储与工作单元抽象。** SessionStore 当前直接封装查询和事务；完整 Repository / Unit of Work 尚未引入，也不是当前必需能力。

- 方案：长期记忆等多个持久化用例出现后，若确有共享事务与查询规则，再抽取有实际职责的存储接口；保持连接和事务所有权清楚。
- 评估：可行性中，需结合新数据契约和迁移；当前优化度低，多用例协作后为中。成本中；风险是通用 CRUD 包装、重复抽象或破坏原子提交。
- 暂缓原因/触发：现有 SessionStore 已满足需求；与 roadmap M2 的记忆变更一起评估，不提前建立通用持久化框架。
- 验收：需要原子提交的变化共用事务，失败整体回滚；不跨线程共享连接，不持有写事务等待网络；旧库迁移和缓存重推可验证。数据库事务不被描述为跨平台恰好一次发送保证。

## 当前保持的设计选择

继续使用 Agent 门面、Provider 策略/适配器、内部简单工厂、Channel 模板方法和 SessionStore 事务封装。建造者、强制单例和动态插件加载没有当前问题支撑，暂不作为实施待办；出现复杂构造、生命周期约束或第三方动态安装需求时，先记录场景与评估。

新增上下文、记忆、MCP、Skill、睡梦整理和常驻运行等能力继续由 [roadmap](roadmap.md)、[能力设计](capabilities.md)、[运行与可靠性](operations.md) 定义范围。上述优化只随真实用例选择，不取代已有可靠性目标。
