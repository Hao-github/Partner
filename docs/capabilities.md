# 管家能力设计

状态：本文件描述待实现能力，作为后续开发约束；除现有对话、历史、模型选择和时间工具外，下述文件加载、命令及模块尚未实现。当前结构见 [架构设计](architecture.md)。

## 能力分工

| 能力 | 内容 | 建议责任位置 | 持久数据 |
| --- | --- | --- | --- |
| SOUL | 身份、语气、价值偏好和相处边界 | core 的上下文组装 | 人工维护的人设文本 |
| 上下文 | 预算、历史选取、记忆和任务说明的组合 | core | 派生摘要按需保存，原始轮次保留 |
| 长期记忆 | 稳定偏好、事实、项目背景及纠正关系 | core 编排，storage 持久化 | 带拥有者、来源和版本的记录 |
| MCP | 连接外部工具、资源和提示等协议能力 | tools 的适配实现 | 配置和凭据引用、必要调用状态 |
| Skill | 某类任务的步骤、参考资料和输出约定 | tools 目录加载，core 选择和组装 | 受控技能目录 |
| 睡梦整理 | 后台提炼、去重和整理记忆 | core 的维护用例，storage 提交 | 处理游标、任务状态和记忆变化 |
| 主动任务 | 到时触发、静默时段、投递和取消 | core 调度，channels 投递 | 任务、触发记录和投递状态 |

这些位置是职责建议，不提前创建文件、基类或插件框架。继续沿用 core、models、providers、storage、tools、channels 分层；Provider 负责协议，不决定人设、记忆召回或技能选择。

## 上下文组装与预算

引入人设或长期记忆时，在 core 增加有实际职责的上下文组装模块，例如 context.py，以普通函数和必要数据类实现。Agent 保留编排和工具循环；渠道继续提供统一消息与历史，不把人格和记忆规则分别写进每个平台。

组装输入包括固定行为约束、人设、当前请求、可用工具及已选 Skill、与请求相关的记忆和最近完整轮次。记忆和外部文档应带来源并作为数据使用，不能通过拼接冒充系统指令。固定能力边界和执行权限由应用控制。

预算要同时覆盖输入、预留输出、工具 schema、工具结果和多轮工具调用。初版可先做字符/字节上限，但必须明确它是保守近似；要保证模型上下文容量，应接入对应计数或明确的适配策略，不能把“20 轮”当成 token 保证。

超限时优先缩短不相关记忆和较早的完整轮次，不拆开工具调用与结果。当前请求本身过大时给出明确提示，不静默删除其核心内容。工具结果保留必要字段和截断说明；文档摘要与原始来源关联。

同时定义单轮总耗时和模型调用预算。单次 HTTP timeout、有限重试和工具轮数只能限制局部步骤，不能直接视为整轮截止时间。后续统计仅记录用量、耗时和状态等元数据。

## SOUL.md 与相处体验

SOUL.md 是人设文本的命名约定。OpenClaw 用它表达人格、语气与边界；该文件不会被本项目自动识别。[OpenClaw 工作区说明](https://docs.openclaw.ai/concepts/agent-workspace)

建议初版仅包含名称、表达方式、主动程度、如何回应情绪和如何表达不同意见。例如“莫念，温和自然、有自己的判断；用户倾诉时先理解感受，需要建议时给具体行动；不编造共同经历”。这只是待采用的内容示例。

- 通过 Config 配置受控路径，在 Agent 初始化时读取 UTF-8 文本，设置大小上限；显式配置但不可读时报告配置错误。
- 未配置时保留默认人设；运行中不逐消息读取文件，修改后重启生效。
- 项目 AGENTS.md 面向开发助手，不作为运行中管家的人设。开发交接文件也不自动加入用户上下文。
- SOUL 不保存私人事实、凭据或工具权限；应用侧固定规则继续独立维护。
- 初版由用户维护人设，后台记忆整理不自动改写。通用模板可入 Git，个人内容使用未跟踪的运行数据路径。

关系连续感依赖稳定人设、可靠记忆和一致回应。初期不建立好感度、情绪分值或自动人格演化状态机；确有交互需求后再设计其语义和用户控制方式。

## 长期记忆及数据一致性

当前 turns 保存成功聊天记录，不等于已经具备长期记忆。第一步支持显式记住、查看、修改、忘记；具体命令名称在实现时确定，当前不能使用。

建议新增 core/memory.py 负责相关性选择、纠正与冲突策略，storage/memory.py 负责查询和写入；两者具有实际职责才创建。跨层传递必要数据类，不暴露数据库连接给 Agent 或渠道实现。

| 字段 | 用途 |
| --- | --- |
| id、owner_key、scope | 标识记录、所属用户及适用范围 |
| kind、content | 区分偏好、事实、项目背景等内容 |
| source_ref、created_at、updated_at | 追溯原消息或明确指令和时间 |
| status、revision、supersedes | 表达有效、待确认、已纠正、已忘记以及并发版本 |

初版 owner_key 使用渠道限定的身份。只有明确绑定后才能跨渠道共享；CLI 的 local 身份也不能默认与某个 QQ 用户合并。召回先过滤拥有者和范围，再按相关性选择，设置数量与大小上限；先用 SQLite 查询，实际需要语义检索时再评估索引。

显式修改优先于旧记录。模型推断不能直接变成已确认事实；未完成事项要区分“被提及”和“已安排任务”。私人记忆留在运行数据库，不写进仓库中的 USER.md 或 SOUL.md。

建议显式记忆变更以结果数据随 Reply 返回，由存储侧与该消息的确认缓存在同一事务提交；同库记忆仓储复用该事务，失败一起回滚。读操作由 core 的记忆用例编排。实现时必须补齐 Reply 契约、旧库迁移、重推幂等和冲突测试，避免先改记忆再因保存失败重复执行。

忘记操作需要定义范围：仅停止召回，还是删除原始聊天、摘要、索引及备份中的相关内容。后台整理必须尊重忘记标记，避免从旧来源重新生成已删除的记忆；备份保留与删除策略需要明确告知用户。

## MCP 与工具执行

MCP 提供外部工具和资源等能力的连接协议；模型侧仍看到统一工具描述和结果。[MCP 架构说明](https://modelcontextprotocol.io/docs/learn/architecture)

首个接入选择一个明确、只读的真实任务。客户端放在 tools 内部，registry 汇总描述和执行分发；Agent 不出现具体服务器分支，Provider 只转换工具协议。MCP 会话/子进程由创建它的组件关闭，最终随 Agent 生命周期释放；资源读取按需进行并限制大小。

在首个接入之前确定服务器启动/连接方式、凭据来源、工具命名冲突、连接与调用超时、总预算和失败提示。远端资源与返回文本均按外部数据处理。配置继续经 Config 提供，不在适配器里重复解析 .env。

引入写操作时，工具执行上下文需要带拥有者、请求标识、允许能力及截止时间等必要信息。授权和参数验证在实际执行边界实施，不能靠 system prompt 或 Skill 文字代替。外部副作用无法加入 SQLite 事务；需单独设计确认、执行记录和幂等键，超时且结果未知时先核对，不能盲目重试。

## Skill 的最小实现

Agent Skills 规范使用含 name、description 的 SKILL.md，按需加载正文和参考资料，可附带脚本及资源。[Agent Skills 规范](https://agentskills.io/specification)

对本项目先选择一个已具备底层工具的流程，例如整理用户提供的项目进展。初版由显式命令选择，读取受控目录中的步骤和格式；有多种稳定任务后再增加自动匹配。内容进入上下文组装，不要求修改 Provider 或渠道协议。

名称只映射到允许目录；不把用户传入字符串直接当任意文件路径。文件名本身不会让模型具备新能力，脚本也不因放进 Skill 目录就自动执行；实际动作经过工具分发和执行策略。初版可只支持 Markdown 步骤与参考资料，脚本执行另作设计。

验收至少覆盖正确选择、未知技能、目录边界、内容大小、缺失工具提示，以及不同 Provider 下的同一任务流程。配置、运行资源路径和缓存的所有权要明确，避免 skills 模块变成另一套环境配置系统。

## 睡梦整理与后台任务

睡梦整理指后台回看近期内容并更新外部记忆。Letta 的 Dreaming 提供了类似的记忆归纳机制；本项目不因此引入其框架或多智能体实现。[Letta 记忆与 Dreaming](https://docs.letta.com/configuration/memory)

在记忆读写、纠正和忘记已经可靠之后，再实现以下流程：

1. 根据持久化游标选取尚未整理的成功轮次，记录来源范围和当前记忆版本。
2. 用有预算的模型调用生成候选变化，去重并区分明确事实与推断；不调用有副作用的业务工具。
3. 提交前重新检查记忆版本、用户纠正与忘记记录，冲突时重新计算或放弃旧候选。
4. 在同一事务中提交记忆变化和游标；失败不推进游标，重复运行不重复创建记录。

初版手动触发，再考虑闲置触发或定时。任务采用独立连接、短事务和受控单实例执行；不持有数据库写锁等待模型，不与前台共享可变对话缓存。明确总 token/耗时预算、取消和重启恢复方式。

睡梦维护与主动提醒是两个用例。提醒还需要持久化任务、时区、取消、重复触发语义和渠道主动发送权限；当前 _send 关联入站消息，不能直接当作通用主动推送接口。平台能力验证后再确定投递契约。
